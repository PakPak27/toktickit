# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a working Requester-facing ticketing MVP: a Requester (selected via a temporary
Development Requester selector) can create an IT support ticket with attachments, view and
search their own tickets in My Tickets, open a read-only Ticket Detail screen, and manage
attachments on their tickets — all on a consistent, responsive Zen Green UI foundation that
later labs will reuse.

## 2. Stakeholder Request Interpretation
The IT department wants Requesters to submit and track their own support tickets without
needing real authentication yet. Since login isn't built until Lab 3, we simulate "who is
logged in" with a Development Requester selector. Once a Requester is selected, the app must
behave as if that person is logged in: they can create tickets, see only their own tickets,
open ticket details, and manage their own attachments — and must never be able to see or
modify another Requester's data, even without real security enforcement yet.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism only)
- Create Ticket screen: form, validation, attachment upload, Ticket Number generation
- My Tickets screen: paginated, searchable, filterable, sortable list of the current
  Requester's own tickets
- Requester Ticket Detail screen: read-only ticket header + attachment management
  (add, download, soft-remove)
- Ownership enforcement: a Requester can only access their own tickets/attachments
- Zen Green UI foundation: reusable colors, typography, field states, button hierarchy
- Responsive layouts (desktop / tablet / mobile) for all three screens above

### Excluded
- Authentication, sessions, passwords, tokens, real authorization
- IT Staff dashboard, ticket claiming, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Ticket status changes beyond initial "New" (no resolve/close/reopen/cancel)
- Administrator functions (user/category/related-system management UI)

## 4. Functional Requirements
- FR-01: The system shall allow selecting an active Development Requester before any
  ticket screen is accessible.
- FR-02: The system shall allow the current Requester to be changed at any time via a
  "Change Requester" action, reloading all Requester-specific data.
- FR-03: The system shall allow the current Requester to create a ticket with Category,
  Related System, Summary, Description, Requested Priority, and optional attachments.
- FR-04: The system shall generate a unique, backend-generated Ticket Number upon
  successful ticket creation.
- FR-05: The system shall list only the current Requester's own tickets in My Tickets.
- FR-06: The system shall allow searching tickets by Ticket Number or Summary text.
- FR-07: The system shall allow filtering tickets by Category, Requested Priority, IT
  Priority, and Current Status.
- FR-08: The system shall allow sorting tickets by Created Date, Ticket Number, and Last
  Updated, ascending or descending.
- FR-09: The system shall paginate the ticket list with a configurable page size.
- FR-10: The system shall allow opening a Ticket Detail screen for any ticket owned by the
  current Requester, and shall deny access to tickets owned by a different Requester.
- FR-11: The system shall allow adding a permitted attachment to an existing owned ticket,
  up to the maximum active-attachment limit.
- FR-12: The system shall allow downloading an active (non-removed) attachment on an
  owned ticket.
- FR-13: The system shall allow soft-removing an active attachment on an owned ticket,
  requiring a removal reason.
- FR-14: The system shall retain removed-attachment metadata (visible, not downloadable)
  rather than deleting the record.

## 5. Business Rules

### Ticket defaults & system-generated values
- BR-01: The official Ticket Number is generated by the backend in the format
  `TKT-YYYY-NNNNNN` (zero-padded sequential number per year) and must be globally unique.
- BR-02: A new Ticket begins with Current Status `NEW`.
- BR-03: Ticket Date is set by the backend to the server time at creation and is read-only.
- BR-04: IT Priority is not set by the Requester; it remains null/unset until Lab 3+
  introduces IT Staff triage.

### Development Requester (testing mechanism)
- BR-05: Lab 2 uses a Development Requester selector instead of login. The selected
  identity is for testing only and is not authentication.
- BR-06: Only active Development Requesters appear in the selector. Inactive Requesters
  are excluded entirely.
- BR-07: The selected Requester persists across page reloads (stored in the browser via
  `localStorage`) until explicitly changed via "Change Requester" or cleared.
- BR-08: If no Requester is selected, any attempt to access My Tickets, Create Ticket, or
  Ticket Detail redirects to the Development Requester Selection screen.

### Ownership
- BR-09: A Ticket belongs to exactly one Requester (the one selected at creation time),
  recorded as `requesterId` on the Ticket.
- BR-10: The backend must enforce ownership on every ticket/attachment read and write —
  the frontend selection is not treated as trusted; every API call re-validates that the
  resource belongs to the `requesterId` provided.
- BR-11: Requesting a ticket or attachment that exists but is not owned by the current
  Requester returns 403/404 (no data leaked), not a raw ticket payload.

### Search, filtering, sorting, pagination
- BR-12: Search matches Ticket Number (exact/partial) or Summary (case-insensitive
  substring match).
- BR-13: Default sort is Created Date descending (newest first); default page size is 10,
  with allowed sizes 10/20/50.
- BR-14: Invalid filter/sort/page parameters are ignored and fall back to defaults rather
  than causing an error.

### Validation & duplicate-submission prevention
- BR-15: Ticket Summary is required, trimmed, 5–120 characters.
- BR-16: Ticket Description is required, trimmed, 10–2000 characters.
- BR-17: Category and Related System are required and must reference active, existing
  records.
- BR-18: Requested Priority is required, one of `LOW`, `MEDIUM`, `HIGH`.
- BR-19: The Submit button is disabled while a request is in flight, preventing duplicate
  ticket creation from a double-click or double-submit.

### Failure behavior
- BR-20: If ticket creation fails after validation passes (e.g., server/database error),
  the form retains all entered values so the Requester does not need to retype anything.
- BR-21: If a ticket is created successfully but attachment upload fails, the ticket is
  still considered created (Ticket Number is shown); the Requester is told which
  attachment(s) failed and may retry adding them from Ticket Detail.

### Attachment rules
- BR-22: Allowed attachment types: JPG, JPEG, PNG, WEBP, PDF only (validated by both file
  extension and MIME type).
- BR-23: Maximum attachment size is 5 MB per file.
- BR-24: Maximum 5 *active* attachments per ticket (soft-removed ones don't count toward
  the limit).
- BR-25: Attachment removal is soft-delete only: the record is flagged `removedAt` /
  `removalReason`, never hard-deleted.
- BR-26: A removed attachment remains visible in the attachment list as metadata (name,
  size, removed date/reason) but returns 410 (Gone) on download or preview attempts.
- BR-27: Only the owning Requester may add or remove attachments on a ticket.
- BR-28: Removing an attachment requires the Requester to confirm and provide a short
  removal reason (required, 3–200 characters).

### Inactive Requesters
- BR-29: An inactive Development Requester cannot be selected and cannot own new tickets;
  existing tickets owned by a now-inactive Requester remain visible only if that Requester
  is somehow still selectable (not applicable in Lab 2 since inactive Requesters are fully
  excluded from the selector).

### Empty / no-results states
- BR-30: If a Requester has zero tickets, My Tickets shows an "empty state" (no tickets
  yet, prompting Create Ticket) rather than a blank table.
- BR-31: If a search/filter combination matches zero tickets, a distinct "no results"
  state is shown (different messaging from the empty state), with an option to clear
  filters.

### Ticket Detail access
- BR-32: Ticket Detail is read-only for all ticket header fields in Lab 2; only
  attachment actions (add/download/remove) are interactive.

### Transition to Lab 3
- BR-33: The Development Requester selector and its `localStorage`-based persistence must
  be isolated behind a single context/module so it can be replaced by real session-based
  authentication in Lab 3 without rewriting ticket screens.

## 6. UI Specification Summary
Full detail lives in `ui-spec.md`. Summary:
- **Application shell:** TokTickIT header (Primary green #006B3C), My Tickets / Create
  Ticket nav links, current Requester name + Change Requester action on the right.
- **Development Requester Selection:** centered card, dropdown of active Requesters,
  Continue button, loading/empty/error states, Lab-2-testing-only disclaimer.
- **Create Ticket:** system-generated fields (Ticket Number placeholder, Ticket Date) shown
  read-only near the top; classification fields (Category, Related System, Requested
  Priority) grouped together; Summary/Description given full width; Attachments below;
  Submit as primary action with busy state.
- **My Tickets:** search bar, filter dropdowns (Category / Requested Priority / IT Priority
  / Status), sortable column headers, paginated table (desktop) / stacked cards (mobile),
  Create Ticket button, empty/no-results/loading/error states.
- **Ticket Detail:** read-only header fields grouped (identification / classification /
  status), Attachments section with upload control, active/removed attachment list,
  soft-remove flow with reason prompt.
- **Responsive:** desktop ≥992px multi-column; tablet 768–991px two-column; mobile <768px
  single-column stacked, touch-friendly buttons, no horizontal scroll.

## 8. API Contract
Full request/response bodies live in `api-spec.md`. Summary of endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | /api/requesters | List active Development Requesters |
| GET | /api/categories | List active Categories (from Lab 1) |
| GET | /api/related-systems | List active Related Systems |
| POST | /api/tickets | Create a Ticket for the current Requester |
| GET | /api/tickets | Paginated, searchable, filterable, sortable list of the current Requester's own tickets |
| GET | /api/tickets/:id | Retrieve one owned Ticket (with attachment summary) |
| POST | /api/tickets/:id/attachments | Upload an Attachment to an owned Ticket |
| GET | /api/tickets/:id/attachments | List Attachment metadata for an owned Ticket |
| GET | /api/attachments/:id/download | Download an active Attachment (ownership-checked) |
| DELETE | /api/attachments/:id | Soft-remove an active Attachment (with reason) |

All Requester-scoped endpoints require a `requesterId` (sent via header
`X-Requester-Id` — a stand-in for a real session, per BR-05/BR-10) and re-validate
ownership server-side on every call.

## 9. Acceptance Criteria
- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is
  saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to open My
  Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is
  requested (by ID), then the Ticket data is not returned (403/404).
- AC-04: Given the Summary field is empty, when the Requester submits the form, then a
  field-level validation message appears and no API call is made.
- AC-05: Given a valid ticket submission on a mobile viewport, when the Requester
  completes the flow, then the confirmation shows the official Ticket Number and the
  layout has no horizontal scroll or clipped content.
- AC-06: Given the backend is unreachable during ticket creation, when the Requester
  submits a valid form, then a safe error message is shown and all entered field values
  are preserved.
- AC-07: Given an attachment larger than 5MB is selected, when the Requester attempts to
  add it, then a clear inline error is shown and the file is not uploaded.
- AC-08: Given a ticket already has 5 active attachments, when the Requester attempts to
  add a 6th, then the upload is rejected with an explanatory message.
- AC-09: Given an active attachment on an owned ticket, when the Requester clicks
  Download, then the original file is downloaded successfully.
- AC-10: Given an attachment is soft-removed with a reason, when the Requester views the
  attachment list, then the attachment still appears with "Removed" status but Download
  is disabled/blocked.
- AC-11: Given Requester A has 3 tickets and Requester B has 2 tickets, when Requester A
  is selected and My Tickets is opened, then exactly Requester A's 3 tickets are shown —
  switching to Requester B shows exactly B's 2 tickets.
- AC-12: Given a search term that matches no tickets, when the Requester searches, then a
  distinct "no results" state is shown (not the same as the zero-tickets empty state).
- AC-13: Given more tickets than one page size, when the Requester navigates pagination,
  then the correct subset of tickets is shown per page with correct page metadata.
- AC-14: Given the Requester sorts by Created Date ascending, when the list reloads, then
  tickets are ordered oldest-first.
- AC-15: Given the Development Requester API fails to load, when the Requester Selection
  screen is opened, then a safe error state is shown (not a blank/broken page).

## 11. Assumptions and Decisions
- Related Systems are never hard-deleted; deactivation uses the existing `isActive`
  flag so foreign-key integrity with historical Tickets is preserved automatically.
- RequesterUser and RelatedSystem seed data extends the existing `server/prisma/seed.ts`
  from Lab 1 (using the same idempotent `upsert` pattern) rather than a separate seed
  file, keeping `npm run prisma:seed` as the single documented seed command.
