### Issue #47 (Actions Taken foundation) review
**Reviewer comment I received:** Punyawat found a real bug: `validateActionTakenInput` decided whether a Follow-up Note was required from `body.followUpRequired === true`, but on a partial `PATCH` that omits `followUpRequired`, the *effective* flag comes from the existing row. So `PATCH { updatedAt, followUpNote: "" }` on an entry that already had `followUpRequired: true` passed validation and saved an empty note alongside a flag that still said follow-up was needed — the exact state BR-06 forbids. He also found the 409 conflict body didn't match `api-spec.md` (a plain string instead of `{ code, message, current }`), that the stale-`updatedAt` check was check-then-write (two simultaneous edits could both pass it), and that `Number.isNaN` let non-integer ids through to a 500 instead of a 404.
**How I responded:** Rewrote the validation to check the *effective* `followUpRequired`/`followUpNote` pair (falling back to the existing row) after loading it, not just whichever field a given request happened to send. Fixed the 409 body to the documented `{ error: { code, message, current } }` shape. Replaced the check-then-write stale check with one atomic `updateMany({ where: { id, ticketId, updatedAt } })`, returning a fresh 409 when `count === 0`. While fixing the race I introduced my own bug — the first version matched on the just-re-read `existing.updatedAt` instead of the client-supplied one, which always matches and defeats the whole check — caught immediately by my own new test. Switched `Number.isNaN` to `Number.isInteger` on all four routes' id parsing.

### Issue #48 (Actions Taken UI) review
**Reviewer comment I received:** Punyawat found that clearing the Attachment Notes field on an edit was silently ignored: `editAttachmentNotes.trim() || undefined` turned an emptied box into `undefined`, and the `PATCH` handler only touches a field when it is present in the request body, so the old value just stayed.
**How I responded:** Sent the trimmed value as-is on edit (never falling back to `undefined`) — the server already turns `""` into `null`. Added regression tests for a successful edit updating the row in place, and for an emptied Attachment Notes field actually sending `""` rather than being omitted.

### Issue #51 (Final hardening, regression, release) review
**Reviewer comment I received:** One blocking bug: wrapping the status route alone in `prisma.$transaction` (my Issue #49 fix above) doesn't close the Actions-Taken-vs-status race, because Postgres's default READ COMMITTED isolation takes no lock on rows a transaction only reads. A concurrent Action Taken write — a separate transaction, touching a different table (`actionTaken`, not `ticket`) — can still commit in between this transaction's gate read and its final write, leaving the gate's decision stale with nothing to catch it. He suggested also bumping `Ticket.updatedAt` on every Action Taken write, so the status route's existing optimistic-concurrency check (keyed on `updatedAt`) would see it. Two further non-blocking notes: the resolution-gate unit test "prioritizes NO_ACTIONS over OPEN_FOLLOW_UP" duplicated an earlier test and didn't actually exercise a case where both could compete; and the `Promise.all` status-concurrency test's comment overstated that it specifically exercises the atomic `updateMany`'s `count === 0` branch, when either rejection path is a legitimate outcome of firing two requests together.
**How I responded:** Took the suggested fix: `POST`/`PATCH .../actions` now bump `Ticket.updatedAt` inside the same transaction as their own write, so the status route's existing CAS catches a concurrent Actions Taken change and rejects as stale rather than letting an invalid gate decision through — no new locking code needed. Reloaded the Ticket client-side after any Action Taken create/edit so the status control's own cached `updatedAt` doesn't go stale from the user's own edit. Removed the duplicate resolution-gate test (there's no input where NO_ACTIONS and OPEN_FOLLOW_UP can actually compete, so no real test could replace it) and reworded the `Promise.all` test's comment to state only what firing concurrent requests actually guarantees. Added a new `Promise.all` test demonstrating the Actions-Taken-vs-status race itself is closed (a RESOLVE racing a follow-up-clearing edit lands on exactly one of two acceptable end states). Corrected the comment in the status route and `tests.md`/this file that had claimed the transaction wrap alone was sufficient — and corrected my own Issue #49 note above claiming this matched my partner's already-correct pattern: he confirmed his equivalent endpoint has the identical gap and is fixing it separately.
